# Experimental protocol

Version 1.0 (as executed). Sections 1-6 are byte-identical to the text in force when the locked test
was opened (first final kernel jobF01, pushed 2026-11-14T12:43Z from commit `4062044`);
`python scripts/protocol_freeze.py` checks this and the rule files listed in section 8. The version
number was not raised before that push: the file still said "0.1 draft" while the locked test ran, and
the 1.0 record (section 8, with the deviations from the plan below) was written on 2026-11-16, before any
locked-test number was read. Sections 1-6 therefore still speak as a plan ("planned sizes", "to be
re-pinned"); what was actually run is in section 8. Changes after a test has been opened require a new
test set and an entry in `DECISIONS.md`.

## 1. Hypothesis

**H1.** Learning to output minimal repair edits on drawn directed graphs improves a small
VLM's accuracy on non-edit relational questions about unseen graphs more than (B) QA
fine-tuning and (C) structural fine-tuning of the same base model with comparable data
exposure and reported compute.

**H0.** Any gain is explained by generic fine-tuning, extra data, output length,
resolution or evaluation shortcuts.

"Unseen" always means unseen root graphs (topologies). Unseen styles and unseen families
are separate, named test conditions. Reachability is used inside the repair goals, so
the claim is transfer from an edit objective to non-edit questions, not the learning of a
new concept.

## 2. Systems

| Code | System | Trained on |
|---|---|---|
| A | frozen base | nothing |
| B | QA-SFT | reachability, critical-edge and basic relation questions |
| C | Structural-SFT | MCDGraph-inspired tasks (masked graph infilling, contrastive graph discrimination, graph description), adapted to the 2B base |
| D | TRACE | minimal repair only (`edited` / `unchanged` / `impossible`) |
| E | parse + solve | base model extracts the graph from the image, exact solver answers |

Base model: `Qwen/Qwen3.5-2B`, revision `15852e8c16360a2fea060d615a32b45270f8a8fc`
(observed on the Hub on 2026-11-10; to be re-pinned at first load). Fallback if it cannot
be run on free GPUs: `Qwen/Qwen3-VL-2B-Instruct`. All arms use the same base and revision.

## 3. Data

Generated by `trace_vr` (generator version in every manifest). Fixed by code and tests:

- Directed simple graphs, no antiparallel pairs, root graphs weakly connected.
- Training families: `layered_dag`, `tree_plus`, `sparse_random`, 5-10 nodes, equal weights.
- Structure OOD: `ring_chords`, `two_cluster`, 11-16 nodes. Family and size change
  together in this split; results on it cannot separate the two. (Open item 7.2.)
- Styles a, b, c for train/dev/ID test; x, y held out for style OOD. Held-out factors:
  colours, node shape and size, font, arrowhead proportions, curved edges (x). The layout
  algorithm is not held out.
- Image 512 x 512. The same pixel budget is used for every system and split.
- Every main sample has an answer-flipping twin (same text, one edge different in the
  image). Root graphs for which a twin cannot be built are discarded and counted.
- Repair categories are balanced through pair types: about 25% each of add, remove,
  unchanged, impossible. This replaces the brief's 35/35/15/15 default; see `DECISIONS.md`.
- Split unit: root graph group. No two graphs from different groups are isomorphic.

Planned sizes (root graphs): pilot train 512, pilot dev 200; main train about 5,000, main
dev 500, ID test 500, style-OOD test 500, structure-OOD test 500, combined-OOD test 250.
Sizes may be reduced before the test is generated if compute requires it.

## 4. Input and output contract

Model input: the image and the instruction text, nothing else. Output: one JSON object.

- Repair: `{"status":"edited","edits":[{"op":"add_edge"|"remove_edge","src":"X","dst":"Y"}]}`,
  `{"status":"unchanged","edits":[]}` or `{"status":"impossible","edits":[]}`.
- Boolean questions: `{"answer": true}` / `{"answer": false}`.

Primary scoring is strict: after stripping surrounding whitespace and at most one Markdown
code fence the response must be exactly one JSON object with exactly the declared keys.
Anything else is a format failure and counts as wrong. Unknown keys are rejected. Labels
are compared after trimming whitespace, case-sensitively. No response is ever repaired
using the ground truth. Format failures are reported separately as well.

A repair answer is applied to the true graph. It is correct iff the status is right and,
for `edited`, the edit is legal (listed addition of an absent edge, or removal of a
present edge), satisfies every goal and uses the minimum number of edits. Any minimal
solution is accepted.

## 5. Metrics

**Primary statistic:** unweighted mean of six accuracies, {reachability, critical edge} x
{ID test, style-OOD test, structure-OOD test}, on main samples (root and edited images).

Reported next to it: each of the six cells; per-task means; critical-pair accuracy (both
twins right); invariance-pair accuracy (both right under relabelling / restyling); format
failure rate; for repair: status accuracy, valid edit rate, minimal repair accuracy; for
E: node/edge precision and recall, direction accuracy; cost (time, device, memory).

Interpretation rules fixed in advance:

- Practical target for calling the result a clear positive: D exceeds the stronger of B
  and C by about 5 percentage points on the primary statistic, not driven by one style or
  one seed. This is a threshold for interpretation, not a prediction.
- The reference baseline (B or C) is chosen on dev with the same statistic before the
  test is opened; both are always shown.
- If either task mean drops by more than 2 points, the result is not described as a
  general improvement.
- Confidence intervals: bootstrap over root graph groups (about 2,000 resamples, fixed
  seed), paired between systems. Three training seeds (3407, 2027, 9173) for a positive
  main claim; seed results are shown individually.
- If E beats D, that is reported and limits any "best practical system" statement.

## 6. Controls

Question-only / blank image; wrong image; label permutation; critical single-edge change;
style change; difficulty slices (nodes, edges, path length, crossings); oracle graph as
text (diagnostic upper bound only, separate table); exact solver on the true graph (must
be 100%, checked by the validator on every sample).

Model-free probes already available (`shortcuts.py`): constant answers, simple text
heuristics, and the text-only ceiling.

## 7. Open items before version 1.0

1. How the model's reasoning or thinking preamble (if any) is handled by the parser. Rule fixed
   2026-11-12 before measurement (DECISIONS): the primary score stays strict (one JSON object,
   optionally in one code fence, nothing else); a response with prose or a reasoning preamble is
   a format failure. The lenient diagnostic (last balanced JSON object, `tasks.lenient_candidate`)
   is reported next to it for every arm, never instead of it. The frozen base on pilot dev
   (MPS smoke, 24 samples) showed no `<think>` block, only plain prose; if a `<think>...</think>`
   block appears in dev outputs, it is treated as prose (no special stripping). Still to measure:
   the share of base responses that are recoverable only leniently (`scripts/colab/base_budget.sh`).
   Measured 2026-11-14 (jobA1, 20 dev roots, `reports/pilot/base_prompt.md`): common prompt strict non-edit macro
   0.1375 vs lenient 0.6125 at 768 tokens (truncation up to 0.900); `direct` 0.600 and `system` 0.625 at 96 tokens with
   no truncation and lenient = strict. Chosen by the rule below: `system`, 96 new tokens.
   Frozen-base prompt (fixed 2026-11-14, before any variant was run; `src/trace_vr/base_prompt.py`): arm A is run on
   the same dev roots under `common`, `direct` (one sentence added after the question: "Do not explain your reasoning.
   Reply with the JSON object only.") and `system` (the same sentence as a system message). The variant with the highest
   strict non-edit macro at its own token limit (item 5 rule) is arm A's prompt; exact tie -> common, then direct. The
   common-prompt result is reported next to it. Trained arms keep the common prompt; scorer, image and question unchanged;
   no answer prefill, no stripping of reasoning.
2. ~~Whether structure OOD should vary family and size separately.~~ Settled 2026-11-12: the
   primary cell `test_struct_ood` keeps the joint shift (new family and 11-16 nodes); a separate
   locked build `pilot_diag` adds `test_family_ood` (ring_chords/two_cluster, 5-10 nodes) and
   `test_size_ood` (ID families, 11-16 nodes), 100 roots each, isomorphism-disjoint from pilot and
   pilot_test. With `test_id` these form a 2x2 table reported next to (not inside) the primary
   statistic. `configs/data_pilot_diag.yaml`, `reports/pilot_diag/validation.json`.
3. ~~Exposure policy per arm and token accounting.~~ Settled 2026-11-12 (DECISIONS): equal
   samples, root groups and images (1,024 / 512 / 1,024 per epoch on pilot train); text and
   target tokens differ by arm and are reported, not equalised (`docs/exposure_pilot_train.md`,
   `scripts/exposure.py`, `tests/test_exposure.py`).
4. ~~Exact adaptation of the three MCDGraph tasks to this generator.~~ Settled 2026-11-12
   (DECISIONS, `arms.py`, `tests/test_arms.py`). Arm C trains on exactly D's images (root +
   repair twin of each root group) and cycles three tasks over the image slots in a fixed order
   (pilot train: 342 description / 341 infilling / 341 matching): (a) graph description, list
   every node and edge; (b) masked infilling, the prompt lists the edge set with max(1, |E|//3)
   edges withheld (seeded by sample id) and states how many are missing, the target is the
   withheld edges; (c) graph matching, one image plus a full edge list, answer true iff it is
   exactly the drawn edge set; negatives (171 true of 341 on pilot train) use the other image's
   edge list, one edit away. (c) is a one-image stand-in for MCDGraph's two-image contrastive
   discrimination, so the arm is reported as "MCDGraph-inspired adaptation", never as MCDGraph.
   Mix is balanced per the brief (MCDGraph's own ratio is 10k:5k:5k). The edge lists in (b)
   and (c) are C's declared extra training input; all arms are evaluated on the same image +
   question. Not re-read for this item: MCDGraph's exact masking scheme. The description-only
   variant stays as ablation arm `C_desc`. Exposure: `docs/exposure_pilot_train.md`.
5. `max_new_tokens` limits, set from dev truncation rates. Procedure fixed 2026-11-12
   (`src/trace_vr/token_budget.py`, `scripts/token_budget.py`, `tests/test_token_budget.py`): one
   greedy dev run per arm at 768 new tokens with token ids saved; truncation and strict/lenient
   scores at 96/192/384/768 are the prefixes of that run; the arm's limit is the smallest candidate
   with every task's truncation <= 2%, else 768 with the residual truncation reported. Not measured
   yet (needs GPU): frozen base via `base_budget.sh job12 10 768`; pilot3 B and D had 0 truncated
   responses at 96 tokens on 200 dev roots (`runs/pilot3_{B,D}/summary.json`), so 96 already meets
   the rule for trained repair/QA arms; C and D2 are checked the same way when trained.
   Outcome (recorded in each run's `summary.json`): every dev evaluation of B, C, D and D2 ran at 96 new tokens with 0
   responses truncated at the limit, at all seeds; arm E ran at 512 new tokens (its graph transcription is longer), 0
   truncated. The 768-token scan with prefixes was run only for the frozen base (jobA1); for the trained arms the rule
   was applied directly, 96 being the smallest candidate. Arm E's 512 is not one of the four candidates (section 8).
6. ~~Whether images are regenerated on the training machine or shipped as files.~~ Settled
   2026-11-12: regenerated on the training/eval machine from the config; the content digest
   (labels, graphs, layouts) must equal the committed manifest's, which `job.sh` and
   `final_eval.sh` assert. Image bytes differ across machines (renderer/font stack) and are not
   required to match; a released benchmark ships the image files of one build with their digest.
7. ~~Minimum graph size for the main build.~~ Settled 2026-11-12 (DECISIONS): measured with
   `scripts/topology_capacity.py` (4,000 generator draws per family and node count,
   `docs/topology_capacity.md`). Five-node cells hold only about 100 (layered_dag), 255
   (tree_plus), 90 (two_cluster), 132 (ring_chords) and 422 (sparse_random) isomorphism classes,
   so they cannot supply ~400 distinct roots per cell; six-node cells reach 400 only with 35-77%
   of draws rejected in four of five families. The main build therefore uses ID nodes [7, 12]
   (size-OOD [13, 18]) with a fixed quota per node count (node count kept on rejection), so
   rejections no longer push the size distribution upward. The pilot, pilot_test and pilot_diag
   builds stay at 5-10 / 11-16 as built; their size skew is reported in the datasheet.
   Quota code path done (`node_quota: equal`, existing digests unchanged). Layout feasibility
   measured (`docs/layout_capacity.md`, `docs/layout_budget.md`): at n=18 only 0.40
   (sparse_random) / 0.61 (layered_dag) of graphs get a clean layout, accepted roots are 3.5-4.4
   edges sparser than rejected ones, and a 4x layout budget does not close that gap. Size-OOD
   is therefore capped at [13, 16] (pooled acceptance >= 0.59 in every ID family at budget 180),
   edges per root are reported per split, and size-OOD is also scored on an edges-per-node-matched
   slice (`scripts/density_slice.py`: roots inside the central 5-95% edges-per-node range of
   pilot train roots, [0.875, 1.667]; reported next to the full split, never instead of it).
   Still open: 512 px readability for the model at 13-16 nodes.

## 8. Version 1.0 record (written 2026-11-16, before any locked-test number was read)

What is frozen, and where it is checked:

- Sections 1-6 above: sha256 of their text at commit `4062044` in `docs/protocol_freeze.json`.
- Evaluation code (package, configs, manifests, evaluation entry points, kernel template): `scripts/kaggle/eval_freeze.py`,
  record `scripts/kaggle/eval_freeze.json`, same commit; every collected final kernel's payload matches it.
- Choices made on dev before the test was opened, each a file unchanged since that commit (`protocol_freeze.py`):
  reference baseline B (`reports/pilot/reference_baseline.json`, 2026-11-13), frozen-base prompt `system` at 96 tokens
  (`reports/pilot/base_prompt.json`, 2026-11-14), locked-test queue of twelve kernels plus the arm A floor
  (`scripts/kaggle/final_queue.json`), external subset and its adapted protocol (`reports/external/vgcure_subset.json`,
  `docs/external_eval.md`, 2026-11-13).
- Base model revision as loaded in every training run: `15852e8c16360a2fea060d615a32b45270f8a8fc` (the one named in section 2).

Deviations from the plan in sections 1-7, all decided before the test was opened unless stated:

1. Scale. The main build (about 5,000 training roots, node range [7, 12]) was not run. The locked test evaluates the
   pilot-scale adapters (512 training roots, 3 epochs, 5-10 nodes) on `pilot_test`: 200 / 200 / 200 / 100 roots for ID /
   style-OOD / structure-OOD / combined-OOD instead of 500 / 500 / 500 / 250 (DECISIONS 2026-11-12). Section 3 allowed
   smaller sizes; it did not foresee dropping the main training build, so every claim is a pilot-scale claim.
2. Order. The test build was generated on 2026-11-12, while items 1 and 5 were still open, not after a 1.0 freeze. Its
   labels were locked in code (`dataset.check_split_allowed`) and no model was evaluated on it before 2026-11-14T12:43Z.
3. Token limits. Item 5's 768-token scan was run for the frozen base only; trained arms used 96 tokens (0 truncated),
   arm E 512 (0 truncated), which is outside the candidate list.
4. Frozen base. Arm A's prompt was chosen on 20 dev roots (120 samples), not the 200 used for the trained arms, and it is
   reported as a floor outside the twelve-kernel comparison (jobF13).
5. Reporting scripts written after the test was opened but before any test number was read (the collectors are
   all-or-nothing and `final_table.py` refuses until all twelve runs are in): `final_pairs.py`, `final_density.py`,
   `final_slices.py`, `final_metrics.py`, `final_floor.py`, `final_reports.py` and `final_primary.py` (2026-11-14/15).
   `final_primary.py` computes the primary statistic exactly as section 5 defines it; the definition predates the test,
   the script does not. Everything else these scripts print is secondary and descriptive.
6. Seed round 9173 of the locked test ran on a collaborator's Kaggle account with the project's adapters (sha256-checked);
   rounds 3407 and 2027 run on the project account in two quota weeks. The software environment of the first seven final
   kernels was not logged (`docs/environment.md`); later kernels print it and `scripts/kaggle/kernel_env.py` flags a change.
7. Controls of section 6 as run: label permutation and style change are the invariance pairs (every final kernel);
   the critical single-edge change is the twin pair; the oracle graph as text was evaluated on dev only (arm D, and B at
   100 roots). Not run on any model: question-only / blank image and wrong image (only the model-free text probes of
   `shortcuts.py` exist). Difficulty slices cover family, size, layout and style; path length and crossings have no slice.
   Item 7's open point (512 px readability at 13-16 nodes) concerns the main build, which was not run.
